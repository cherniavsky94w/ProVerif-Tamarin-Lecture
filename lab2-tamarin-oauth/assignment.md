# Практична робота 2. Пошук вразливостей у потоці OAuth 2.0 з кодом авторизації за допомогою Tamarin

**Тривалість:** 2 академічні години в аудиторії, оформлення звіту вдома.
**Інструмент:** Tamarin 1.12 з Maude (установка: [../INSTALL.md](../INSTALL.md)).
**Звіт:** за [../report-requirements.md](../report-requirements.md) і розділом «Звіт» нижче.

## Мета

Навчитися моделювати протокол правилами переписування мультимножин, формулювати леми з часовими точками, запускати Tamarin в автоматичному та інтерактивному режимах, читати граф атаки й пояснювати атаку на вебпротокол в термінах браузера, клієнта й сервера авторизації.

## Що треба знати перед заняттям

- Лекція: правила Tamarin (`[ премісія ] --[ дії ]-> [ висновок ]`), лінійні та персистентні (`!`) факти, `Fr`, `In`, `Out`, леми `All ... ==> ...` і `exists-trace`, обмеження (`restriction`).
- Потік OAuth 2.0 з кодом авторизації: RFC 6749, розд. 4.1. Параметри `client_id`, `redirect_uri`, `state`, `code`, `iss` (RFC 9207).
- Загрози й захисти OAuth 2.0: RFC 9700 (OAuth 2.0 Security Best Current Practice).

## Протокол, який моделюємо

Вхід на сайт-клієнт через «Увійти за допомогою AS» (потік з кодом авторизації):

1. Браузер → клієнт: користувач натискає «Увійти» й обирає сервер авторизації (AS).
2. Клієнт → браузер: перенаправлення на AS з параметрами `client_id`, `redirect_uri`, `state`.
3. Браузер → AS: запит авторизації; користувач уводить логін і пароль.
4. AS → браузер: перенаправлення на `redirect_uri` з параметрами `code`, `state`, `iss`.
5. Браузер → клієнт: запит на `redirect_uri` (callback) з `code`, `state`, `iss`.
6. Клієнт → AS: обмін коду на токен, клієнт автентифікується своїм `client_secret`.
7. AS → клієнт: ідентифікатор користувача (абстракція access token і userinfo). Клієнт прив'язує сесію браузера до цього користувача.

Учасники моделі:

| Учасник | У моделі | Чесний? |
|---|---|---|
| браузер користувача | факт `!Browser(b, as, u, pw)`: браузер `b`, акаунт `u` з паролем `pw` на AS `as` | так |
| клієнт | `!Client(c)`; `client_id = redirect_uri = c`; секрет для кожного AS у `!ClientCfg(c, as, sec)` | так |
| сервер авторизації | `!AS(as)`; зареєстровані клієнти `!ClientReg(as, cid, ruri, sec)`, акаунти `!Account(as, u, pw)` | так |
| зловмисник | мережа поза TLS; власний браузер `'adv'`; власні акаунти на чесних AS; власні клієнти, зареєстровані на чесних AS (`!AdvHost`); власні AS (`!DAS`) | ні |

Як змодельовано вебсередовище:

- TLS: лінійні факти `ToClient`, `ToAS`, `ToBrowser`, `ToTokenEP`. Зловмисник не читає й не змінює чесний трафік TLS, але може надсилати власні запити зі свого браузера (`Adv_ToClient`, `Adv_ToAS`).
- Користувач може перейти за посиланням, яке надіслав зловмисник: на сторінку авторизації AS (`B_FollowAuthzLink`) або на callback клієнта (`B_FollowCbLink`).
- Перенаправлення на хост зловмисника (`B_Redirect_To_AdvHost`) віддає зловмиснику всі параметри URL.
- Після завантаження сторінки callback її URL разом з кодом може витекти (заголовок Referer, історія браузера): правило `C_Login` публікує код після входу.
- Браузер реалізує стандартну поведінку перенаправлення 307: повторно надсилає тіло попереднього POST запиту на нову адресу (`B_Repost_*`).

## Властивості

| Лема | Зміст |
|---|---|
| `executable` (exists-trace) | досяжність: чесний користувач може увійти в чесний клієнт; очікувано `verified` |
| `session_integrity` | клієнт прив'язує сесію браузера `b` до користувача `u`, лише якщо `b` справді браузер `u`. Порушується і тоді, коли зловмисник отримує сесію чесного користувача, і тоді, коли браузер чесного користувача входить в акаунт зловмисника (login CSRF) |
| `password_secrecy` | пароль чесного користувача не стає відомим зловмиснику |

Для лем типу `exists-trace` результат `verified` означає «трасу знайдено», для решти `verified` означає «доведено для всіх трас», `falsified` означає «знайдено контрприклад (атаку)».

## Варіанти

Номер варіанта: `((номер у списку групи − 1) mod 6) + 1`. Модель варіанта: `models/oauth_v<N>.spthy`. У кожній моделі один з учасників не виконує перевірку, якої вимагають RFC 6749, RFC 9207 або RFC 9700. Яку саме, ви маєте встановити за графом атаки.

## Хід роботи

### Крок 0. Перевірка установки (5 хв)

```bash
tamarin-prover --version | head -2
maude --version
```

### Крок 1. Розминка: протокол Нідгема–Шредера в Tamarin (20 хв)

```bash
cd warmup
tamarin-prover --prove nspk.spthy
```

1. Наприкінці виводу (`summary of summaries`) леми `types` і `executable` мають бути `verified`, `nr_secrecy` і `responder_injective_agreement` мають бути `falsified`.
2. Запустіть графічний інтерфейс: `tamarin-prover interactive .`, відкрийте <http://127.0.0.1:3001>, оберіть теорію `NSPK`, клацніть на лемі `nr_secrecy`, далі `autoprove`. Розгляньте граф: вузли з назвами правил моделі (`I_1`, `R_1`, …) є кроками учасників, решта вузлів є кроками, якими зловмисник виводить нові знання (розшифрування, складання кортежів тощо); стрілки показують, як факти й повідомлення переходять між кроками.
3. Порівняйте граф з атакою Лоу з ПР1. Знайдіть на графі момент, коли зловмисник дізнається `nr`.
4. Виправте модель (протокол Нідгема–Шредера–Лоу) і переконайтеся, що всі леми `verified`.
5. Тимчасово приберіть з моделі лему `types` і спробуйте довести `executable` (`tamarin-prover --prove=executable nspk.spthy`; через хвилину зупиніть Ctrl+C). Що відбувається? Поясніть (ключові слова: часткові деконструкції, `[sources]`). У графічному інтерфейсі подивіться вкладку `Raw sources` / `Refined sources` до і після.

### Крок 2. Перший запуск свого варіанта (10 хв)

```bash
cd ../models
tamarin-prover --prove oauth_v<N>.spthy > oauth_v<N>.out.txt
tail -12 oauth_v<N>.out.txt
```

Запишіть результати лем і час перевірки (`processing time`).

### Крок 3. Читання графа атаки (25 хв)

1. `tamarin-prover interactive .`, оберіть свою теорію, для кожної леми з результатом `falsified` виконайте `autoprove` і розгляньте граф.
2. Знайдіть правило `C_Login` (подія `LoggedIn`) наприкінці графа і пройдіть назад: який браузер (`b`) отримав сесію, для якого користувача (`u`), звідки клієнт узяв `code` і `state`, звідки їх дізнався зловмисник (вузли `!KU(...)`).
3. Текстовий доказ у файлі виводу читається так само: рядок `solve( !KU( ~code ) ... )` з наступним `case <Правило>` означає «зловмисник дізнався код через правило `<Правило>`».
4. Знайдіть у моделі правило, яке пропустило повідомлення, хоча не мало б, і визначте, якої перевірки бракує.
5. Збережіть зображення графа для звіту.

### Крок 4. Відповідність реальній вразливості (10 хв)

Назвіть клас атаки та знайдіть її опис у RFC 9700 (розділ і назва атаки), а за можливості в статті Fett, Küsters, Schmitz (CCS 2016) або в реальних звітах про вразливості. Поясніть, яку рекомендацію RFC 9700 порушено.

### Крок 5. Виправлення та повторна перевірка (15 хв)

Внесіть мінімальне виправлення. Після нього `executable` і обидві леми безпеки мають бути `verified`. Якщо `executable` став `falsified`, виправлення зламало протокол і доведення інших лем нічого не варте.

### Додаткове завдання (до +10 балів, на вибір одне)

1. **Мутаційне тестування.** Візьміть свою виправлену модель і приберіть іншу перевірку (у клієнта або AS), не ту, що була у вашому варіанті. До запуску запишіть прогноз: яка лема порушиться й чому. Запустіть і порівняйте з прогнозом.
2. **Нова властивість.** Сформулюйте лему «код авторизації, виданий чесному користувачу для чесного клієнта, ніколи не стає відомим зловмиснику». Доведіть або спростуйте її на виправленій моделі й поясніть результат. Чи означає він ваду протоколу?

## Звіт

Загальна структура: [../report-requirements.md](../report-requirements.md). Особливості цієї роботи:

- у таблиці результатів (розд. 2.7) усі леми для трьох моделей: розминка після виправлення, ваш варіант, ваш варіант після виправлення; кількість кроків доказу та час перевірки;
- діаграма атаки має показувати браузер жертви, браузер зловмисника, клієнт і AS окремими учасниками; позначте, які переходи відбуваються через TLS, а які через посилання чи перенаправлення, підконтрольні зловмиснику;
- в описі моделі (розд. 2.5) поясніть, як у Tamarin змодельовано TLS і чому зловмисник не може прочитати факт `ToClient`;
- в архіві: `nspk.spthy` з вашим виправленням, `oauth_v<N>.spthy`, `oauth_v<N>_fixed.spthy`, текстовий вивід Tamarin для кожної моделі, зображення графа атаки.

Приклад рядка таблиці результатів (значення умовні):

| Лема | `oauth_v<N>.spthy` | `oauth_v<N>_fixed.spthy` |

| `session_integrity` | falsified (8 кроків) / verified | verified (47 кроків) |

## Контрольні запитання

1. Чим лінійний факт відрізняється від персистентного? Як це використано в моделі, щоб код авторизації був одноразовим?
2. Що означає лема `exists-trace` і чому для `executable` бажаний результат `verified`?
3. Як у моделі змодельовано TLS? Яку атаку модель не знайшла б, якби TLS було змодельовано як `Out`/`In`?
4. Навіщо в OAuth параметр `state`? Від якої атаки захищає точне порівняння `redirect_uri`? Що таке mix-up атака і як її зупиняє параметр `iss`?
5. RFC 9700 рекомендує PKCE навіть для конфіденційних клієнтів. Від яких атак з ваших шести варіантів PKCE захистив би й без основного виправлення? Від яких ні?
6. Чому Tamarin іноді не завершує доведення? Що таке часткові деконструкції і як їх усуває лема `[sources]`?
7. ProVerif чи Tamarin: який інструмент ви обрали б для цієї моделі й чому?
8. Яких атак на OAuth ця модель принципово не може знайти (наприклад, через абстракцію браузера, відсутність часу, ідеальний TLS)?
